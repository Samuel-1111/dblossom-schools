# Portal Specification Audit

The uploaded specification requires shared HSL-token portal styling, exact login copy and field-level errors, a localStorage-backed Admin password override, nine module-specific Admin workflows, Student result filtering with report-card PDF generation, and a Teacher Class Teacher versus Teaching Staff branch with editable subject-score grids.

The current implementation already has the three routes, server-signed local Admin credentials, Supabase-backed student/teacher/result data, assigned-class loading, attendance recording, and a report-oriented Student dashboard. The concrete gaps are that the shared login currently uses generic copy and styling; Admin uses a server cookie rather than the specified localStorage override (the server guard should be preserved for security); Admin Teachers, Results, Payments, Events, Gallery, Subjects, and Settings are generic or incomplete module views; the Student dashboard displays normalized grade rows rather than the specified Result search/report-card flow; and the Teacher dashboard saves individual grade rows rather than the specified create/update result object with subject-score grid, session, comments, overall percentage, and role-specific view-only behavior.

Implementation priority: preserve secure server-side authentication, then improve shared portal login validation/loading copy and the highest-risk Teacher/Student workflow contracts without exposing the Supabase service-role key. Admin media records now load through the protected endpoint, but event/gallery mutations and uploads remain incomplete.
